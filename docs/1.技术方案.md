# weibo-assistant 技术架构

## 1. 目标与边界

项目用于长期监听微博网页版群聊，将消息结构化保存到 PostgreSQL，并按通知规则通过企业微信中转服务提醒使用者。

微博没有满足本项目需求的稳定群聊订阅 API，因此采集端依赖网页版内部网络协议。这意味着：

- 登录态、页面结构和消息协议可能变化。
- 服务需要处理页面重载、登录失效、CDP 连接变化和重复消息。
- Chrome Profile 属于敏感凭据，必须按密钥保护。
- 当前 API 主要面向受控的 Tailscale/内网环境。

## 2. 进程与模块

生产环境由三个独立进程组成：

| 进程 | 命令 | 职责 |
| --- | --- | --- |
| API | `weibo-assistant server` | HTTP API、健康检查、Prometheus 指标、浏览器 WebSocket |
| 监听 | `weibo-assistant monitor` | Chrome、CDP、消息解析、入库、outbox 通知 worker |
| 前端 | `weibo-assistant frontend` | Go 静态文件服务，托管 `frontend/dist` |

代码模块：

```text
cmd/weibo-assistant/   命令分派和日志初始化
internal/app/          进程编排、通知 worker、运行时指标
internal/browser/      Chrome、CDP、页面探测、消息解析
internal/config/       环境变量和按命令校验
internal/httpapi/      REST、健康检查、指标、WebSocket
internal/migrate/      迁移版本、校验和、事务锁
internal/notifier/     企业微信中转客户端
internal/store/        PostgreSQL 数据访问
frontend/              Vue + TypeScript 前端
migrations/            版本化 SQL
```

## 3. 数据流

```text
微博聊天页
  -> Network.webSocketFrameReceived
  -> parseNetworkMessages
  -> CreateMessage PostgreSQL 事务
       -> upsert group/user
       -> insert message/attachments
       -> match notification_rules
       -> insert notification_outbox
       -> update group timeline
  -> pg_notify
       -> server LISTEN
       -> browser WebSocket
       -> Vue 增量更新

notification worker
  -> claim outbox with FOR UPDATE SKIP LOCKED
  -> call wework relay
  -> sent / retry / failed
  -> notification_events
```

## 4. 浏览器与 CDP

monitor 使用独立 Chrome 用户目录：

```text
--user-data-dir=<WEIBO_PROFILE_DIR>
--remote-debugging-address=127.0.0.1
--remote-debugging-port=<CHROME_DEBUG_PORT>
```

启动过程：

1. 创建权限为 `0700` 的 Profile 目录。
2. 查找 Chrome/Chromium/Edge 可执行文件。
3. 打开微博聊天页。
4. 通过 `/json/list` 选择聊天 page target。
5. 判断是否跳转登录页。
6. 按 ID 或名称选择目标群。
7. 对目标 WebSocket Debugger URL 启用 Network domain。

健康检查会重新读取真实 target，而不是复用启动时快照。target 变化时取消旧监听并绑定新 target；定时重载通过 `Page.reload` 在当前 target 内完成。

CDP 调试端口只绑定本机，不应通过公网或 Tailscale 暴露。

## 5. 消息解析与图片补全

首选数据源是微博 WebSocket frame。解析结果包含：

- 微博消息 ID
- 微博群 ID、群名
- 微博发送人 ID、昵称、头像
- 消息类型、正文、发送时间
- 原始 payload
- 图片 FID 和附件元数据

图片消息可能只包含 FID。monitor 会从以下来源补全 URL：

- WebSocket 中已有的图片字段。
- XHR/fetch 响应体中的 FID 与图片 URL。
- 页面 DOM 中已经加载的图片地址。
- 历史回溯或前端渲染遇到待解析 FID 时，由 monitor 通过已登录聊天页请求 `meta_query.json` 并保存 `thumbnail_240`。

前端不会直接持有微博 Cookie。它只创建 `media_resolution_jobs` 任务，monitor 领取后使用 CDP 页面中的 JSONP 请求完成解析；数据库更新会发出 `message_updated`，再通过 WebSocket 刷新当前消息。FID -> URL 缓存是线程安全的，并设置 TTL 和容量上限。CDP 请求追踪在完成、失败和 WebSocket 关闭时清理，同时有硬上限保护。

图片 URL 还需通过关联校验：`msget_thumbnail`/`msget` 的 `fid` 必须与附件 fid 一致；不直接携带数字 fid 的 `sinaimg.cn` 图床地址必须位于同一消息图片对象中。`role_icon`、头像、徽章、等级、勋章、挂件和头像框等装饰路径不会参与图片附件提取。

## 6. 历史同步与消息补偿

实时 WebSocket 与历史接口承担不同职责：WebSocket 提供低延迟消息，`query_messages.json` 提供确定性的分页补偿。历史请求通过聊天页的 CDP target 执行 `fetch`，因此自动携带当前 Chrome Profile 的微博 Cookie，不在后端复制或持久化 Cookie。

接口分页规则：

- `max_mid=0` 请求最新一页。
- 响应消息按旧到新排列。
- 下一页使用当前页最旧消息 ID 作为 `max_mid`。
- `max_mid` 是排他边界，下一页不会重复返回该边界消息。
- 每页默认 20 条；任务通过 `max_pages` 设置请求上限。

### 6.1 统一任务模型

三种同步都写入 `history_sync_jobs`，由 monitor 中的 worker 领取：

| mode | 触发时机 | 默认页数 | 通知策略 |
| --- | --- | --- | --- |
| `startup` | monitor 启动并准备好目标群 | 1000，通常在追到 `stop_mid` 前提前停止 | 不通知 |
| `recovery` | CDP 或微博 WebSocket 断开后重新连接 | 100 | 新补入消息正常匹配通知规则 |
| `manual` | 前端按钮、消息列表向上翻页 | 前端消息回溯 1000，按需翻页 1 | 不通知 |

任务状态：

```text
pending -> running -> completed
                   -> failed
```

同一个群只允许一个 `pending/running` 任务。worker 使用 `FOR UPDATE SKIP LOCKED` 领取任务；运行锁超过 10 分钟后可重新领取。每页更新游标、请求页数、扫描数和新增数，状态变化通过 PostgreSQL `NOTIFY` 和前端 WebSocket 实时广播。

### 6.2 统一停止规则

三种模式都会尽量在明确边界处停止。启动补偿优先使用 `stop_mid`：monitor 创建任务时记录数据库中已有的最新微博消息 ID，worker 从最新页向前扫描，直到遇到这个 ID 才停止。没有 `stop_mid` 的任务退回到通用规则：遇到任务创建前数据库中已经存在的微博消息 ID 后停止。

任务创建时间作为数据库快照边界。这样可以正确处理历史同步和实时 WebSocket 并发写入：

1. `startup` 遇到 `stop_mid` 代表已经追到启动前的数据库边界，立即停止。
2. 没有 `stop_mid` 时，任务创建前已存在的消息代表已经进入连续的已知历史区间，立即停止。
3. 任务创建后被 WebSocket 抢先写入的消息只跳过，不作为停止边界。
4. 最终仍由 `weibo_messages.dedupe_key` 唯一约束防止重复入库。

其他停止条件包括：达到指定开始时间、接口无更多消息、游标不再前进或达到最大页数。停止优先级是 `stop_mid` 优先，其次才是任务创建前已存在消息。

### 6.3 启动补偿

monitor 启动时先确保目标群存在于数据库，并读取该群当前最新微博消息 ID 作为 `stop_mid`。聊天页 CDP target 可用后，worker 从最新页开始向前同步，直到追到 `stop_mid`；如果一直追不到，最多请求 1000 页后以 `max_pages_reached` 停止，避免接口异常造成无限循环。即使网页版已经自动请求过最近消息，主动同步仍会重叠一段；数据库去重负责合并，避免页面加载时序或分页边界造成漏消息。

启动补偿用于覆盖 monitor 整体退出、服务器重启或部署更新期间的消息。历史补偿消息不会生成企业微信通知，避免重启后集中发送旧提醒。

### 6.4 WebSocket 断线补漏

monitor 同时观察 CDP 网络监听和微博页面 WebSocket 状态。首次断开时记录：

- 断开时间 `requested_from`。
- 断线前数据库最新消息 ID `stop_mid`，用于诊断。
- 重连时间 `requested_to`。

重连后创建 `recovery` 任务，从最新页向前扫描，直到遇到任务创建前已有消息。新补入且位于断线时间窗口内的消息会写库、推送前端，并正常匹配企业微信通知规则。CDP 网络监听本身使用有上限的指数退避在进程内重连，monitor 不会因为一次 EOF 直接退出。

### 6.5 消息回溯

前端“消息回溯”支持填写最早时间和可选区间结束时间。API 创建 `manual` 任务后立即返回 `202 Accepted`，实际请求由持有微博登录态的 monitor 异步完成；前端不直接访问微博接口。

消息回溯从数据库当前最旧消息 ID 的前一页开始，连续向前请求，直到遇到已有消息、到达指定时间或达到页数上限。前端消息列表向上加载完本地数据后，会创建一个 `max_pages=1` 的按需同步任务；完成后通过实时事件加载新写入的更早消息，并保持滚动位置。

消息回溯只做归档和前端展示，不触发企业微信通知。

## 7. 数据一致性与去重

消息写入使用单个 PostgreSQL 事务，覆盖：

1. 群组 upsert。
2. 用户 upsert。
3. 消息插入。
4. 附件插入或补录。
5. 群组最后消息时间。
6. 通知规则匹配和 outbox 入队。

去重优先使用微博消息 ID；缺失时使用群、发送人、类型、正文和时间生成 SHA-256。数据库 `dedupe_key` 唯一约束是最终保障。

`pg_notify` 在事务提交后以 best-effort 执行。实时刷新失败不会把已经提交的消息伪装成入库失败，前端断线重连后会重新拉取数据。

## 8. 通知规则与 outbox

通知规则可按以下字段组合匹配：

- 数据库内部群 ID、用户 ID
- 微博原始群 ID、发送人 ID
- 群名、发送人昵称
- 消息类型

规则至少需要一个条件，避免空规则匹配全部消息。

`TARGET_GROUP_*` 和 `TARGET_SENDER_*` 在 monitor 启动时同步为“环境变量默认通知规则”。环境变量 ID 优先于名称。

每个“消息 + 规则”最多存在一个 outbox 任务。worker 使用 `FOR UPDATE SKIP LOCKED` 领取，失败后从 5 秒开始指数退避，最大间隔 15 分钟，默认最多尝试 8 次。锁定超过 5 分钟的 sending 任务可被重新领取。

状态：

```text
pending -> sending -> sent
                   -> retry -> sending
                   -> failed
```

## 9. 数据库模型

核心表：

| 表 | 用途 |
| --- | --- |
| `weibo_groups` | 群组与最后消息时间 |
| `weibo_users` | 微博用户 |
| `weibo_messages` | 规范化消息和原始 payload |
| `weibo_message_attachments` | 图片等附件 |
| `notification_rules` | 启用/停用的匹配规则 |
| `notification_outbox` | 可靠通知任务 |
| `notification_events` | 每次通知结果 |
| `monitor_status` | monitor 心跳、最后消息和错误 |
| `monitor_runtime_metrics` | monitor 跨进程指标快照 |
| `history_sync_jobs` | 启动补偿、断线补漏和消息回溯任务及进度 |
| `media_resolution_jobs` | 前端或回溯触发、由 monitor 使用微博登录态消费的图片 FID 解析任务 |
| `schema_migrations` | 已执行迁移和校验和 |

迁移文件必须使用 `NNN_name.sql`。迁移器在事务中取得 advisory lock，校验已执行版本的 SHA-256，再执行并登记新版本。

## 10. API 与实时更新

主要读取 API：

```text
GET /api/groups
GET /api/users
GET /api/messages
GET /api/groups/{id}/messages
GET /api/groups/{id}/history-sync
GET /api/notification-rules
GET /api/notification-events
GET /api/monitor/status
GET /api/ws
```

写 API：

```text
POST  /api/messages
POST  /api/groups/{id}/history-sync
POST  /api/notification-rules
PATCH /api/notification-rules/{id}
POST  /api/notification-events
```

`POST /api/dev/messages` 只在 `APP_ENV=development` 注册。

服务限制 JSON 请求体为 `1 MiB`，拒绝未知字段和多个顶层 JSON 值；列表 limit、ID、时间和布尔参数严格校验。

server 监听 PostgreSQL channel `weibo_assistant_events`，收到事件后加载最新记录并广播给前端。浏览器 WebSocket 强制版本 13、客户端 masking、帧大小上限和读写 deadline。

历史同步任务状态通过 `history_sync_updated` WebSocket 事件广播；历史消息仍使用统一的 `message_created` 事件，不需要前端维护第二套消息协议。

## 11. 健康检查与指标

- `/livez`：API 进程存活，不访问依赖。
- `/readyz`：数据库、monitor freshness、最后消息和通知积压。
- `/healthz`：兼容 `/readyz`。
- `/api/monitor/status`：monitor 状态、心跳年龄和 stale 阈值。
- `/metrics`：Prometheus 文本格式。

monitor 每 15 秒将以下快照写入 PostgreSQL：

- 浏览器和 CDP 状态、重连数。
- 最近 60 秒及累计解析消息数。
- 入库成功/失败、去重数。
- 通知成功、重试和最终失败数。
- tracked requests、图片缓存、内存和 goroutine。

前端根据 `lastHeartbeatAt` 和 `staleAfterSecs` 每秒计算 freshness，心跳过期后显示故障状态。

## 12. 日志与隐私

生产 `info` 日志只记录：

- 微博消息 ID
- 群 ID、发送人 ID
- 消息类型
- 正文字符数
- 16 位短 SHA-256

正文、原始 payload、DOM 候选文本和群选择文本仅在 `debug` 日志中输出，并做长度截断。生产环境应保持 `LOG_LEVEL=info`，限制 journald 读取权限和保留周期。

## 13. 部署与故障恢复

systemd 分别管理 server、monitor 和可选 frontend。Chrome 或 monitor 异常退出后由 systemd 重启；monitor 自身能够处理页面重载、target 变化和 CDP 网络监听退避重连。

历史任务保存在 PostgreSQL。monitor 进程退出不会丢失 `pending` 任务；超时的 `running` 任务可在重启后重新领取。其他未完成事项见 [5.优化建议.md](./5.优化建议.md)。
