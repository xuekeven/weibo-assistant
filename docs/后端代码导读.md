# 后端代码导读

这份文档面向准备从前端转向全栈的开发者。建议先理解调用关系，再深入 CDP、SQL 和 WebSocket 的协议细节。

## 1. 用前端概念理解目录

| Go 目录 | 职责 | 可以类比为 |
| --- | --- | --- |
| `cmd/weibo-assistant` | 读取命令并启动应用 | `main.ts` |
| `internal/config` | 加载并校验环境变量 | 环境配置模块 |
| `internal/app` | 创建依赖、启动任务、连接各层 | 应用 bootstrap / composition root |
| `internal/httpapi` | 路由、参数解析、HTTP 响应 | Router + Controller |
| `internal/store` | SQL、事务、数据库模型 | Repository / API 数据层 |
| `internal/browser` | 启动 Chrome、监听微博网络事件 | 浏览器适配器 / 数据采集 SDK |
| `internal/notifier` | 调用企业微信中继 API | 第三方 API client |
| `internal/migrate` | 执行数据库结构升级 | schema migration runner |

Go 的 `internal` 目录表示这些包只能被当前项目内部引用，不能被其他项目当作公共库导入。

## 2. 推荐阅读顺序

1. `cmd/weibo-assistant/main.go`：了解有哪些子命令。
2. `internal/config/config.go`：了解程序依赖哪些环境变量。
3. `internal/app/app.go`：先只看 `RunServer` 和 `RunMonitor`，掌握进程如何组装。
4. `internal/httpapi/server.go`：查看路由表，再按兴趣阅读对应 handler。
5. `internal/store/store.go` 和 `messages.go`：理解连接池、事务和消息写入；统计与导出可对照阅读 `httpapi/message_exports.go` 和 `store/message_exports.go`。
6. `internal/store/outbox.go`：理解可靠异步通知。
7. 最后阅读 `internal/browser/monitor.go` 和 `cdp.go`。这里包含协议解析，复杂度最高。

测试文件可以和实现文件配对阅读，例如看完 `image_cache.go` 后立刻阅读 `image_cache_test.go`。

## 3. 一次 HTTP 请求如何流动

以 `GET /api/messages` 为例：

```text
浏览器请求
  -> httpapi.Server 的路由
  -> handleListMessages 解析 query 参数
  -> store.ListMessages 执行 SQL
  -> handler 将结果编码为 JSON
  -> 浏览器收到响应
```

`httpapi` 不直接拼 SQL，`store` 也不知道 HTTP 状态码。这种分工让每层只处理一种问题。

统计与导出遵循相同边界：HTTP 层严格校验群聊 ID、时间边界和格式，store 层只查询具有数字微博 UID 的成员消息，并排除 `system`、`event`、`recall`。CSV 编码还会中和表格公式前缀，避免聊天正文被电子表格软件当作公式执行。

## 4. 一条微博消息如何入库

```text
Chromium 收到微博响应
  -> browser 通过 CDP 读取响应体
  -> 解析为 NetworkMessage
  -> app 中的 OnMessage 回调
  -> 转换为 CreateMessageParams
  -> store.CreateMessage 开启事务
  -> 写入群、用户、消息、附件和 outbox 任务
  -> 提交事务
  -> PostgreSQL NOTIFY
  -> server 推送 WebSocket 事件给前端
```

这里有两个重要设计：

- `dedupe_key` 是数据库唯一键。重连导致同一消息被重复采集时，不会重复入库。
- 通知任务和消息在同一事务中创建。不会出现消息已经保存、通知任务却丢失的状态。

## 5. outbox 为什么可靠

直接在消息回调里请求企业微信有两个问题：第三方接口变慢会阻塞采集；进程崩溃会丢失待发送通知。

outbox 将“需要发送通知”先保存为数据库任务：

1. worker 领取一条到期任务并标记为 `sending`。
2. 发送成功后标记为 `sent`。
3. 发送失败后标记为 `retry`，按指数退避计算下次时间。
4. 达到最大次数后标记为 `failed`。
5. `sending` 状态长时间未完成时允许重新领取，以恢复进程崩溃前的任务。

`FOR UPDATE SKIP LOCKED` 类似一个由 PostgreSQL 实现的并发安全任务队列。

## 6. 初学 Go 时重点关注的写法

### context.Context

`context` 传递取消信号和超时。systemd 停止服务时，根 context 被取消，HTTP 服务、Chrome 和后台 goroutine 会沿调用链退出。

### defer 与事务

`defer` 在当前函数返回前执行，常用于关闭连接、停止 ticker 和回滚事务：

```go
tx, err := pool.Begin(ctx)
if err != nil {
    return err
}
defer tx.Rollback(ctx)

// 执行多条 SQL……
return tx.Commit(ctx)
```

提交成功后再调用 `Rollback` 是安全的，因此所有提前返回路径都得到了保护。

### goroutine 和 channel

`go fn()` 类似启动一个轻量后台任务。channel 用于在 goroutine 之间传递结果。项目中的后台任务都应监听 `ctx.Done()`，否则停服时可能无法退出。

### 错误包装

`fmt.Errorf("load messages: %w", err)` 在保留原始错误的同时增加上下文。上层日志因此能看出失败发生在哪个阶段。

### 参数结构体

函数参数较多时项目使用 `CreateMessageParams` 一类结构体，作用类似 TypeScript 的 options object：字段含义清楚，也便于增加可选参数。

## 7. 修改代码时的边界

- 新 HTTP 接口：路由和输入输出放在 `httpapi`，SQL 放在 `store`。
- 新环境变量：放在 `config.Config`、`Load`、相应的 `ValidateXxx` 和 `.env.example`。
- 新数据库字段：新增 migration，不修改已经执行过的 migration。
- 新第三方通知渠道：协议调用放在 `notifier`，重试调度仍由 outbox worker 负责。
- 新微博解析规则：放在 `browser`，不要让该包直接操作数据库。

提交前至少运行：

```bash
gofmt -w cmd internal
go test ./...
go vet ./...
```

## 8. 调试入口

- `LOG_LEVEL=debug`：开启调试日志，生产环境不要长期启用。
- `GET /livez`：确认 API 进程存活。
- `GET /readyz`：确认数据库、monitor 新鲜度和通知积压状态。
- `GET /api/monitor/status`：查看 monitor 当前页面和最近错误。
- `GET /metrics`：查看采集、持久化、通知和内存指标。

遇到问题时先判断属于 HTTP、数据库、浏览器采集还是第三方通知，再进入对应包定位。
